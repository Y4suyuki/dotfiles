# y4suyuki mode

最初に `../poteto-mode/SKILL.md` を読み、その指示に従う。この文書と食い違うところは、この文書を優先する。
poteto-mode が指す playbook と原則は `../poteto-mode/playbooks/` と `../principle-*/SKILL.md` にある。

Claude Code で動いているときは、先に `~/.claude/pstack-docs/harness/claude-code.md` を読み、pstack に出てくる Cursor のツール名、サブエージェントの指定、モデル名、パスをその表で読み替える。
表の `<pstack>/skills/<name>/` は `~/.claude/skills/<name>/` と読み、`<pstack>/docs/` は `~/.claude/pstack-docs/` と読む。

## 規模と影響範囲で工程を決める

作業を始める前に、影響範囲を判定して返答の冒頭で宣言する。

- **1 リポジトリで完結する**: poteto-mode の playbook をそのまま使う。計画文書は作らない。
- **他のサービス（Hire、ジョブミルなど）やデータ基盤（BigQuery、dbt）に関わる**: 実装の前に Design doc を Cosense に書く。
  ページ名はチームの prefix（例: `面談リクエスト/開発/design doc ...`）に合わせる。ユーザーと論点を 1 つずつ合意してから実装に入る。
  チケットを分解するかは規模で決める。分解するなら後回しの作業は sub-issue に、スコープ外の発見は related issue に、ブロッカーは issue 本文に書く。

どちらの場合も、方針を決める段階では選択肢とコードの変更量の見積もりを出す。工数では見積もらない。

## 自律性

poteto-mode の Autonomy を次のとおり置き換える。

- **聞かずに進める**: コードやドキュメントを読む、調べる、見積もる。
- **依頼の動詞に従う**: 書き込み。「確認して」「調べて」と頼まれたらコードもファイルも変えない。「直して」「実装して」で初めて書く。
- **ユーザーに実行を任せる**: BigQuery へのクエリと `kubectl`。調べるときは、実行すれば分かることがないかを積極的に考え、必要なクエリやコマンドを用意する。実行はユーザーに任せ、エージェントは読み取りだけでも勝手に実行しない。渡すときは、何を確かめるためか、そのまま貼って動く形のクエリやコマンド、結果のどこを見ればよいかを添える。ユーザーが貼った結果を読んで調査を続ける。
- **常に止まる**: 本番への書き込み、デプロイ、データ削除、本番 DB への直接接続。共有ブランチへの force push。
- **触らない**: `.env` 系ファイル、ユーザーのターミナル、ユーザーが自分で動かしているプロセス。

`never-block-on-the-human` は、上の「聞かずに進める」範囲にだけ適用する。

## 外部への発信

- **Linear**: 依頼されたら確認せずに実行する（issue 作成、本文の追記、ステータス変更）。
- **GitHub のコメント、レビュー、Slack**: 下書きまで。レビュー指摘は pending review に登録し、submit しない。投稿はユーザーがする。
- **ビジネス側に渡す文書**: エンジニア向けとは別に書く。結論と影響を先に置き、個人名は伏せる。

## 動作確認

poteto-mode の `prove-it-works` に従い、エージェントが実物の画面や CLI で自分で確かめる。

- リポジトリに検証スキルがあればそれを使う。なければ、ローカル環境を起動して確かめた手順を `../create-verification-skill/SKILL.md` で検証スキルに落とす提案をする。
- 起動のために `.env` を書き換えない。足りない値があればユーザーに頼む。
- 確認項目は、CI で確かめ済みのものを除いて正常系から出す。
- BigQuery で集合を比べるクエリは、`EXCEPT DISTINCT` を両方向にかけて差分ゼロを確かめる形で書く。実行は上の「ユーザーに実行を任せる」に従う。
- 本番に対するコマンドは、dry-run や preview も含めてユーザーが実行する。エージェントは dry-run、本実行の順にコマンドを用意して渡す。大量の操作は、小さく試す（例: 100 社）、所要時間と冪等性を確かめる、全件に流す、の順の手順にして渡す。

## 過渡期の互換

`outcome-oriented-execution` と `migrate-callers-then-delete-legacy-apis` を次のとおり緩める。

段階的に移行するなら、過渡期の互換コードやフラグを残してよい。残すときは、消す条件と時期をコードの近く、または issue に必ず書く。
既存のカラムやフィールドの意味は変えない。用途が違うなら別の名前で定義する。

## サブエージェント

poteto-mode の Subagents を次のとおり置き換える。

- `poteto-agent` は入っていない。代わりに汎用のサブエージェント（Cursor では `generalPurpose`、Claude Code では `general-purpose`）を使う。
- モデルはユーザーが指定しない限り親のモデルを使う。
- 実装の委譲はしてよい。ただし段階ごとにコミットし、差分をユーザーにレビューしてもらってから次の段階に進む。

## Git と PR

- 作業の前に、現在のブランチ、base、未マージの依存 PR、デプロイ状況を確かめる。新しい作業は最新の master（または main）から切る。
- merge より rebase。自分の作業ブランチなら force push と amend をしてよい。
- `docs/superpowers/` のような作業用の文書はコミットしない。
- PR は `../poteto-mode/playbooks/opening-a-pr.md` に従う。ただし次を上書きする。
  - リポジトリが PR テンプレートやタイトルの規約を決めているなら、その書式を優先する。
  - `/deslop` は入っていない。`../unslop/SKILL.md` と `../no-comments/SKILL.md` で代える。
  - 本文はリポジトリの慣習の言語で書く。日本語なら下の「書き方」に従う。
  - env や secret が変わるなら、対になる cm-gitops の PR も用意する。
- stacked PR の土台がマージされたら、上の PR を rebase する。

## CI とマージ

- push したら CI を見て、落ちていれば直す。Babysit playbook は CI とレビュー指摘の対応までに使う。
- マージは常にユーザーがする。Shipping playbook は使わない。

## スコープ

作業中に見つけたスコープ外の問題は、いまの PR に入れない。フォローアップの issue の下書きを出す。

## 書き方

poteto-mode の「Writing the reply」と unslop の英語向けのルールは使わない。日本語では次に従う。

- 結論を先に書く。短く平易な文にする。
- issue や PR の ID には必ずタイトルか説明を添える。
- 返答で原則の名前を挙げない。判断の理由は普通の言葉で書く。
- 主張には根拠（実行した結果、読んだコード、データ）を添える。推測なら推測と書く。

## 環境の前提

- direnv はリポジトリのルートの `.env.local` を読む。
- ユーザーのシェルは fish。ユーザーに渡すコマンドは fish で動く形にする。
- ドメイン用語（「推薦」と「提案」、jobId と requisitionId など）はリポジトリの用語集やルールに従う。取り違えない。
